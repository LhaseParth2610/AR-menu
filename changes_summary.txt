# Technical Summary of Application Updates

This document provides a detailed technical summary of recent modifications to the TasteAR application, focusing on iOS compatibility and performance optimization.

## 1. iOS Augmented Reality (AR) Compatibility

### 1.1. Problem Description
The AR functionality was not operational on iOS devices. The root cause was traced to the `<model-viewer>` web component's requirements for iOS. While standard on most platforms, Apple's AR Quick Look, the default AR viewer on iOS, requires the 3D model to be in the `.usdz` format. The application was only providing a `.glb` model, causing the AR activation to fail on iPhones and iPads.

### 1.2. Solution Implemented
To resolve this, the application's data and presentation layers were updated to support the `.usdz` format for iOS devices.

#### 1.2.1. Data Structure Modification
The `static/menu-data.js` file, which serves as the data source for the menu, was updated. Each menu item object within the `menuData` constant was systematically updated to include an `Iospath` property. This property holds the path to the corresponding `.usdz` model file.

**Example of the modified data structure in `static/menu-data.js`:**
```javascript
{
    id: 1,
    name: "Classic Cheeseburger",
    // ... other properties
    modelPath: "models/dish1.glb",  // Path for Android/Web
    Iospath: "models/dish1.usdz",   // Path for iOS Quick Look
    modelScale: 0.22,
    // ... other properties
}
```

#### 1.2.2. Dynamic Attribute Binding
The client-side JavaScript in `static/menu-script.js` was already designed to handle this data. The `openFoodDetail` function dynamically sets the `src` and `ios-src` attributes on the `<model-viewer>` element when a user selects an item. With the `Iospath` now available, this function correctly provides the right model format to each platform.

**Relevant code snippet from `static/menu-script.js`:**
```javascript
// ... inside openFoodDetail(itemId)
const modelViewer = document.getElementById('foodModel');
if (modelViewer && item.modelPath) {
    modelViewer.src = '/static/' + item.modelPath; // For standard viewers
    modelViewer.setAttribute('ios-src', '/static/' + item.Iospath); // For iOS
}
```

## 2. 3D Model Performance Optimization via Draco Compression

### 2.1. Problem Description
The 3D models, stored as standard `.glb` files, were uncompressed. Their relatively large file sizes resulted in noticeable loading delays, negatively impacting the user experience, especially on slower network connections.

### 2.2. Solution Implemented
A compression pipeline using Google's Draco library was implemented to reduce the size of the 3D models.

#### 2.2.1. Compression Tooling
The `gltf-pipeline` Node.js package was installed as a local project dependency. This command-line tool allows for applying Draco compression to glTF and GLB files.

#### 2.2.2. Compression Process
Each `.glb` model in the `static/models/` directory was processed using the `gltf-pipeline` tool. The compression was applied directly to the files, overwriting them with their smaller, compressed versions.

**Command used for compression:**
```bash
npx gltf-pipeline -i [input_model.glb] -o [input_model.glb] --draco.compressionLevel=10
```
The `--draco.compressionLevel=10` flag ensures the highest level of compression is applied, maximizing file size reduction.

#### 2.2.3. Client-Side Decoding
To enable the browser to render these compressed models, the `<model-viewer>` component must be configured with the path to the Draco decoder library. This was achieved by adding the `draco-decoder-path` attribute to the `<model-viewer>` element in `templates/menu.html`.

**Modification in `templates/menu.html`:**
```html
<model-viewer id="foodModel"
    draco-decoder-path="https://www.gstatic.com/draco/v1/decoders/"
    ar
    ar-modes="webxr scene-viewer quick-look"
    ...>
</model-viewer>
```
When a compressed model is loaded, `<model-viewer>` fetches this decoder library. The library then decompresses the model's geometry on the client-side (in the user's browser) before rendering it. This workflow reduces the network transfer size, leading to significantly faster model loading times.
